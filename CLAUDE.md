# template-aws-api

BDD and contract driven AWS Lambda API. `specs/` (OpenAPI contract + feature
files) is the requirement; `task ci` is the definition of done.

- The skeleton (router, validation, harness, gates, CI, infra) is the same for
  every API and is already built. Do not rebuild or restructure it; write only
  the business logic the specs describe: `steps/`, `src/operations/`,
  `src/routes.ts`, `src/domain/`, `src/store/` and their tests.
- Tools come from `mise.toml`; every command is a task - run `task` to list them.
- To implement or change the API from the specs, use the `implement-api` skill.
- `specs/` is read-only unless the user asks for a spec change.
- Never weaken a gate (Taskfile, cucumber config, spec/route checks, lint rules, CI) to get green.
- Contract standards are lower snake_case (`rules/house.yaml`); rules for one
  API go in `.spectral.yaml`.
- `src/generated/` is generated by `task generate`; do not edit or commit it.

## Branches

- `main` is the template. `example/spec` is `main` plus the example spec;
  `example/implementation` is `example/spec` plus its implementation. The
  example branches exist to be read and compared, not developed on.
- Every skeleton change is made on `main` and then merged down:
  `main` → `example/spec` → `example/implementation`. Never change a skeleton
  file on an example branch.
- The only differences allowed are: `specs/` and the README's status banner
  (`example/spec`); plus `src/routes.ts`, `src/operations/`, `src/domain/`,
  `src/store/`, `steps/*.ts` other than `world.ts`, and their tests
  (`example/implementation`). `git diff main example/spec --stat` and
  `git diff example/spec example/implementation --stat` should list nothing else.
- CI is red by design on `main` and `example/spec` and green on
  `example/implementation`.
